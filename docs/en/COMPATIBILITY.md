# OriginLore Compatibility Notes

Applies to: OriginLore 2.1.0  
Environment: Minecraft 1.21.1, Fabric Loader 0.19.2 or newer, Java 21

## Installation requirements

| Where | What to install |
| --- | --- |
| Server / modpack server | OriginLore + Fabric API + Fabric Loader 0.19.2 or newer |
| OP client that needs the admin GUI | the same OriginLore JAR + Fabric API |
| Regular player clients | nothing |

Even without the mod installed, regular players see and use the names, lore, rarity, food effects, enchantments and attribute modifiers generated by the server. All of it is written into the item itself as vanilla data components and parsed by the vanilla client.

The admin GUI is only open to operators at permission level 2 or above. The server never sends the config to an under-privileged client.

## Automated tests

The repository contains two test suites:

- **18 JUnit unit tests** covering config schema and legacy migration, atomic saves and corruption fallback, config revisions, network fragment transport and size limits, and three-tier rule merging with source resolution. `./gradlew build` runs them automatically, and GitHub Actions runs them on every push and pull request.
- **12 GameTests** running inside a real Minecraft server, covering component application and restoration, preservation of third-party `custom_data`, variant stability across refresh and duplication, the furnace/smoker/blast furnace pause-and-reroll behaviour, same-variant stacking versus different-variant isolation, and the `UNKNOWN` fallback when an item enters a player inventory directly. These need to be run separately:

```powershell
.\gradlew.bat runGametest --console=plain
```

Both suites pass in full under Fabric Loader 0.19.2 and 0.19.3.

## Automatically recognised sources

The following paths are recognised without any extra configuration:

- Loot tables: chest and structure loot, dungeons, fishing, archaeology, piglin bartering, trial chamber vaults
- Drops: block drops, entity drops
- Commands: items created by `/give` and similar commands
- Recipes: crafting table, furnace / blast furnace / smoker smelting, stonecutting, smithing table transformation and trimming
- Anvil
- Player inventory: items handed out by other mods calling `insertStack` or `setStack` directly

Items whose origin cannot be traced reliably — for example items that already existed before the mod was installed, or mod-added creation paths that bypass the standard generation routes — are classified as `UNKNOWN`. You can configure a rule for `UNKNOWN` to adopt them in bulk; OriginLore will not guess them into the chest or crafting source.

## Coexistence with other mods

- OriginLore never modifies any third-party mod's JAR, config file or resources.
- It only adopts the item fields you explicitly list in the config. Unconfigured fields fully preserve data written by vanilla, by players and by other mods, including anything another mod stores under `minecraft:custom_data`.
- Adopted items keep their own source identity, variant ID, config revision and the original values of managed fields under `minecraft:custom_data.originlore`, stored separately from third-party data so neither overwrites the other.
- After a field is deleted from the config, OriginLore restores the original component patch recorded before that item was first adopted, rather than leaving an empty value behind.
- When another mod hands an item directly to a player inventory it goes through the `UNKNOWN` fallback; if that mod already wrote components of its own, OriginLore only adds the fields the config asks for.

## Known limitations

- Behaviour that another mod hardcodes in Java without expressing it through standard data components cannot be faked with advanced components alone and needs dedicated integration work.
- OriginLore does not scan unloaded chunks and does not rewrite offline world saves directly. Those items are handled lazily the next time they load.
- The advanced data component editor only accepts components that exist in the current registry and have a persistence codec. Invalid or nonexistent components are rejected by the server and never reach the config or the item.
- Random variants are rolled exactly once, when the item is first adopted. Later config hot-modifications, restarts, duplication, splitting, dropping, chunk reloads and player reconnections never re-roll.

## Building from source

```powershell
.\gradlew.bat test runGametest build --console=plain
```

The default target is Fabric Loader 0.19.2. For a quick regression run against 0.19.3:

```powershell
.\gradlew.bat test runGametest '-Ploader_version=0.19.3' --console=plain
```

Quote Gradle property arguments that contain dots when using PowerShell.

The production JAR is written to `build/libs/originlore-2.1.0.jar`. Deploy that JAR — not the `-dev` or `-sources` variants.
