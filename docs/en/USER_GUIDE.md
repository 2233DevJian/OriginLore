# OriginLore User Guide

This guide covers OriginLore 2.0.1, Minecraft 1.21.1 and Fabric Loader 0.19.2.

> **About the GUI language.** The admin interface is currently Chinese-only. Source type names are the exception — they come from the game's language file, so they follow your Minecraft language and appear in English under `en_us`. Every other button, tab, field and status message is a hardcoded Chinese string. Throughout this guide, GUI labels are quoted as `` `中文` `` followed by an English gloss, for example `` `保存` (Save) ``. Match the Chinese characters on screen, not the gloss.

## 1. Installation and permissions

The server must have:

- OriginLore.
- Fabric API.
- Fabric Loader 0.19.2 or a newer 1.21.1-compatible version.

Any client that needs to open the admin GUI installs the same OriginLore JAR. Regular players do not need the OriginLore client and can still see and use every item property the server generates.

Only operators at permission level 2 or above can read or modify the config. After joining a world, press `O` to open the admin GUI; the keybind can be changed under Minecraft's Options → Controls.

## 2. Your first lore line in five minutes

This example makes every sweet berry, from any source, show one lore line by default.

1. Join a single-player world or a server and press `O`.
2. Wait until the top-right shows the server's config revision instead of `正在同步...` (Syncing...) or `无管理员权限` (No admin permission).
3. Click `+ 新增` (Add).
4. Type `minecraft:sweet_berries` into `物品 ID` (Item ID). After a few characters you can press `Tab` to complete it.
5. Keep `基础规则` (Base rule) selected on the left.
6. On the `[文本]` (Text) page, enter into the lore field: `Sweet and tangy berries. Not bad!`
7. Each line becomes one separate lore entry; insert a newline whenever you want more than one.
8. Click `保存` (Save) at the very bottom.

Once the save succeeds the config revision increments automatically, managed items in online players' inventories and in loaded objects start refreshing, and items loaded later also pick up the rule.

## 3. Understand the three rule tiers first

The left side of the editor is the rule tree for the current item; the right side edits whichever tier is selected. Blue text marks the tier you are editing.

| Tier | Purpose | Example |
| --- | --- | --- |
| `基础规则` (Base rule) | Defaults shared by this item in every situation | All sweet berries are "sweet and tangy" |
| `来源规则` (Source rule) | Overrides the base rule only when one specific source matches | Berries from chests get a different food profile |
| `变体规则` (Variant rule) | Rolled by weight on first creation within a single source | Chest berries split into fresh, stored and rotten |

The final application order is:

```text
base rule -> matching source rule -> variant rolled on first creation
```

A field you leave empty means "inherit" — it never blanks out the item's own value. When a field that OriginLore already adopted is deleted from the config, the item gets back the original component value recorded before it was first adopted.

## 4. Using source rules

### Adding a source

1. On the item rule page, click `+ 来源` (+ Source) on the left.
2. A new source defaults to `未知来源` (Unknown source).
3. Keep that source selected and click `来源设置` (Source settings) at the top right.
4. Click the source type button and pick the source you want from the dropdown.
5. Fill in a loot table ID or recipe ID when you need an exact match; leave it empty to match the whole source category.
6. Click `应用` (Apply) to return to the item rule page.

Source type names, as they appear in the English client and in the config:

| English GUI | Config value | Applies to |
| --- | --- | --- |
| Block drop | `BLOCK_DROP` | items produced by mining, harvesting or breaking a block |
| Chest loot | `CHEST_LOOT` | items generated by structure, dungeon and similar loot tables |
| Entity drop | `ENTITY_DROP` | mob and other entity death drops |
| Fishing | `FISHING` | fishing loot |
| Archaeology | `ARCHAEOLOGY` | archaeology loot from suspicious blocks |
| Piglin barter | `BARTER` | piglin bartering loot |
| Gift | `GIFT` | items given by villagers and similar systems |
| Vault | `VAULT` | items produced by trial chamber vaults |
| Command | `COMMAND` | items created by `/give` and similar commands |
| Crafting | `CRAFTING` | shaped and shapeless crafting table recipes |
| Smelting | `SMELTING` | furnace, blast furnace and smoker recipes |
| Stonecutting | `CUTTING` | stonecutter recipes |
| Smithing | `SMITHING` | smithing table transformation, upgrade or trim |
| Unknown source | `UNKNOWN` | legacy items, or unrecognised mod-added creation paths |

Loot table ID examples:

```text
minecraft:chests/village/village_taiga_house
minecraft:chests/village/village_weaponsmith
```

Recipe ID example:

```text
minecraft:iron_sword
```

If a concrete ID cannot be obtained at runtime, OriginLore only tries the rules in that same source category which have no ID constraint. It never misassigns the item to a different source.

## 5. Using random variants

A variant must belong to a source; you cannot attach one directly to the base rule.

1. Select a source on the left first.
2. Click `+ 变体` (+ Variant).
3. Select the newly created `variant_1`. A `当前变体权重` (Current variant weight) field appears at the top right of the main editor; you can also click `来源设置` (Source settings) to edit it on the full source page.
4. Rename the variant ID to something stable and unique, such as `fresh`, `stored` or `rotten`.
5. Enter a weight, for example `80` and `20`, or `80%` and `20%`. Weights are relative probabilities and do not have to add up to 100; the list on the left shows each variant's weight and live probability.
6. If you edited on the `来源设置` (Source settings) page, click `应用` (Apply) to return to the main editor. Only `保存` (Save) at the bottom of the main editor actually commits.
7. Keep the variant selected and edit its own lore, food or attributes on the pages to the right.

For example, three variants weighted 6, 3 and 1 give roughly 60% `fresh`, 30% `stored` and 10% `rotten`. At least one variant must have a weight above 0.

Variants are rolled exactly once, when the item is first adopted. Config hot-modification, restarts, duplication, splitting, dropping, chunk reloads and player reconnections never re-roll, and different variants never stack together by mistake. Identical variants stack normally even when one came from a furnace and the other from a smoker, as long as the resulting components match.

### Random output from furnaces, smokers and blast furnaces

To stop a single output slot from holding different variants, OriginLore pauses the machine after each item: once the current item has fully cooked and had its variant written, the machine stops consuming fuel and advancing progress until a player or hopper takes the output. The next item is then rolled against the newest weights. If the config was just hot-modified, the change affects only that new roll — already-finished output is never altered. The machine never stops mid-cook because it "predicted" the next variant.

## 6. A complete berry example

Goal: foraging in the wild behaves normally, while chests may yield fresh, stored or rotten berries.

1. Give the base rule of `minecraft:sweet_berries` the lore `Sweet and tangy berries. Not bad!`
2. Add a source and set it to `箱子战利品` (Chest loot). Leave the loot table empty to cover every chest, or enter a specific ID to cover just one kind.
3. Under that source, create `fresh`, `stored` and `rotten` with weights 6, 3 and 1.
4. Leave the food fields empty on `fresh` so it inherits the base rule and the vanilla food component.
5. Select `stored`, set its lore to "Berries stored for a long time. They taste a bit off...", switch to the `[食物]` (Food) page and lower the nutrition and saturation.
6. Select `rotten`, write rotten lore, and set even lower nutrition and saturation.
7. On the `[食物]` (Food) page of `rotten`, click `编辑食物状态效果` (Edit food status effects) and add nausea, hunger and similar effects with their trigger chances.
8. Back in the main editor, click `保存` (Save) at the very bottom — only then is it committed to the server.

If foraging in the wild should differ from the default, add a `方块掉落` (Block drop) source rule as well; otherwise it simply inherits the base rule.

## 7. Tool and weapon example

Using an iron sword:

1. Add or edit `minecraft:iron_sword`.
2. Add a `工作台合成` (Crafting) source with recipe ID `minecraft:iron_sword` to describe swords the player crafted.
3. Add a `箱子战利品` (Chest loot) source with loot table `minecraft:chests/village/village_weaponsmith` to describe swords from a weaponsmith's chest.
4. Edit name, lore, durability or attribute modifiers separately under each source.
5. When you want random quality, add several variants under the relevant source.

The random attack damage range on the `[数值]` (Values) page is rolled and persisted on first creation. For anything more complex, or that needs a specific slot, use `能力` (Capabilities) → `属性修饰符` (Attribute modifiers).

## 8. The four main pages

### `[文本]` (Text)

- `自定义名称` (Custom name): the item's custom name; leaving it empty means the name is not adopted.
- Lore: one line per row.
- `B`, `I`: bold and italic.
- `颜色:` (Colour): cycles through colours; `继承` (Inherit) means no colour is forced.

The simple style set here applies to both the name and the lore edited through the form on this tier. When you need different colours per line, hover events or more complex text, use `能力` (Capabilities) → `完整规则 JSON` (Full rule JSON) to edit vanilla Text JSON directly.

### `[数值]` (Values)

- `最大堆叠` (Max stack).
- `最大耐久` (Max durability) and `当前耐久损耗` (Current damage).
- `稀有度` (Rarity): accepts `COMMON`, `UNCOMMON`, `RARE`, `EPIC`, or 0 to 3.
- `自定义模型数据` (Custom model data).
- `攻击伤害随机范围` (Random attack damage range).

A range requires both a minimum and a maximum, and the minimum cannot exceed the maximum.

### `[食物]` (Food)

- `营养值` (Nutrition).
- Saturation.
- Eat time in seconds.
- Whether the item can be eaten at full hunger.
- Chance-based status effects.

`继承` (Inherit) means this tier does not override the tier above it. When you intend to replace the whole food component, nutrition and saturation should normally be filled in together.

### `能力` (Capabilities)

- `附魔与存储附魔` (Enchantments & stored enchantments).
- `属性修饰符` (Attribute modifiers).
- `工具挖掘规则` (Tool mining rules).
- `食物状态效果` (Food status effects).
- `高级数据组件` (Advanced data components).
- `完整规则 JSON` (Full rule JSON).
- Three-state toggles for `防火` (Fire resistant), `隐藏提示` (Hide tooltip) and `隐藏附加` (Hide additional).

Three-state buttons cycle `继承` (Inherit) → `是` (Yes) → `否` (No) → `继承` (Inherit). "Inherit" here is not the same as "No": it lets the rule above, or the item's own value, keep applying.

## 9. Three levels of saving in the sub-editors

This is the easiest thing to get wrong:

| Button | What it actually does |
| --- | --- |
| `保存条目` (Save entry) | Writes the current enchantment, attribute, effect, tool rule or advanced component into the local transactional copy |
| `应用到规则` (Apply to rule) | Hands the whole sub-editor copy back to the current base / source / variant rule |
| `保存` (Save) at the bottom of the main editor | Submits the complete item config to the server for validation and writing to disk |

So clicking only `保存条目` (Save entry) in the attribute editor and then leaving the main editor changes nothing on the server. The correct order is usually `保存条目` (Save entry) → `应用到规则` (Apply to rule) → `保存` (Save) in the main editor.

Clicking `取消` (Cancel) on any page discards that page's unapplied copy instead of passing it up a level; clicking `取消` (Cancel) in the main editor abandons the whole item editing transaction.

## 10. Completion and dropdown controls

Item, loot table, recipe, enchantment, attribute, status effect, block and data component IDs are all completed from a registry catalog supplied by the server.

- Type the beginning of an ID and wait for the completion list to appear.
- `↑` / `↓`: move between candidates.
- Mouse wheel: scroll a long list.
- `Tab` or `Enter`: accept the current candidate.
- `Escape`: close the current completion or selection list.
- Mouse click: select a candidate directly.

The popup expands upward or downward automatically depending on the space left on screen. The form underneath only becomes clickable again after the popup closes.

## 11. Attributes, enchantments and advanced components

### Attribute modifiers

- Attribute ID example: `minecraft:generic.attack_damage`.
- The modifier ID must be a valid, stable namespaced ID, for example `originlore:rusty_sword_damage`.
- `add_value`: adds a flat amount.
- `add_multiplied_base`: adds a proportion of the base value.
- `add_multiplied_total`: adds a proportion of the final value.
- The slot decides when the modifier applies, for example `mainhand`, `offhand`, `head`.

### Enchantments

Regular enchantments and stored enchantments are managed separately. Enchantment levels must be integers; the server validates that each enchantment ID exists.

### Advanced data components

The advanced editor is for vanilla or modded data components that the standard forms do not cover:

1. Enter the component ID, for example `minecraft:food`.
2. In `SET` mode, provide that component's own JSON value.
3. `REMOVE` mode means the component is explicitly removed.
4. Click `保存条目` (Save entry), then `应用到规则` (Apply to rule).

The server validates the JSON against the current Minecraft registry and that component's persistence codec. Components that do not exist, are not persistable or cannot be resolved are rejected on save, rather than having arbitrary JSON written onto an item.

## 12. Saving, hot refresh and reloading from disk

The final `保存` (Save) in the GUI goes through these steps:

1. The client submits the config revision it saw when the editor was opened.
2. The server re-validates permission, revision, item ID, components and values.
3. On success the config is written via a temporary file and an atomic replace.
4. The revision increments and is broadcast to online administrators.
5. Online inventories, ender chests, equipment, loaded containers, block inventories and item entities begin refreshing incrementally.

If another administrator has already saved a newer revision, the stale editor receives a version conflict prompt. Cancel the edit, reopen the item, then modify it — this avoids overwriting someone else's config.

The on-disk config lives at:

```text
config/originlore/item_components.json
```

After editing that file by hand, an operator can run:

```text
/originlore reload
```

If the file is corrupt or component validation fails, the server refuses the reload and keeps using the last known-good config.

## 13. Common status messages

| Message | Cause and remedy |
| --- | --- |
| `无管理员权限` (No admin permission) | The player is not an operator at permission level 2+ |
| `服务器不支持管理协议` (Server does not support the admin protocol) | The server has no OriginLore installed, or client and server protocols are incompatible |
| `未连接` (Not connected) | You left the world or the connection dropped; the open editor can no longer commit |
| `版本冲突` (Version conflict) | Another administrator, or a disk reload, produced a newer revision; reopen the editor |
| `修改被拒绝` (Modification rejected) | Read the server validation error shown in the GUI and fix the offending ID, value or JSON |
| No completions appearing | Confirm you are connected and syncing has finished; the ID may also not exist in the server's registry |

## 14. Important behavioural boundaries

- OriginLore never scans unloaded chunks and never modifies an offline world save directly.
- Legacy items whose source cannot be traced are `UNKNOWN`; they are never guessed into the chest or crafting source.
- Configured fields are adopted by OriginLore; unconfigured fields keep the data written by players, by vanilla and by other mods.
- Behaviour a mod hardcodes in Java without expressing it through standard data components cannot be faked with advanced components alone and needs dedicated compatibility work.
- After deleting an item's entire config, already-loaded managed items that had original values recorded restore those components on the next refresh; unloaded objects are handled lazily when they load later.
